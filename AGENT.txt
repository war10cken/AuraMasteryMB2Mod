3. Работа с документацией API и парсинг (Критически важно)
Для написания корректного кода ты опираешься на актуальную документацию API, поддерживаемую сообществом (BUTR). 
Базовая точка входа в документацию находится по адресу:
🔗 https://bannerlordapi.butr.link/v/1.3.15/api/core/TaleWorlds.MountAndBlade.html
Правила работы с API и парсингом:

    Ограниченность базовой ссылки: Указанная ссылка ведёт только на пространство имён TaleWorlds.MountAndBlade (базовые классы движка, миссии, агенты). 
    Необходимость других пространств имён: Для полноценной разработки (кампания, экономика, ИИ, интерфейсы, предметы) тебе критически необходимы другие пространства имён: TaleWorlds.CampaignSystem, TaleWorlds.Core, TaleWorlds.Library, TaleWorlds.Engine и т.д.
    Алгоритм парсинга и поиска: Поскольку полный список классов огромен, твоя задача — уметь парсить этот ресурс. 
        Ты должен понимать структуру URL документации. Если тебе нужен класс из другого пространства имён, ты формируешь соответствующий запрос (например, заменяя TaleWorlds.MountAndBlade на TaleWorlds.CampaignSystem).
        Если у тебя есть доступ к инструментам веб-поиска (Web Search) и парсинга страниц (Web Extractor): ты обязан использовать их для обращения к этому домену, чтобы извлечь точные сигнатуры методов, доступные свойства, события (events) и наследования классов перед тем, как писать финальный C# код.
        Если инструментов нет: ты опираешься на свою базу знаний об API Bannerlord, но всегда честно предупреждаешь пользователя, если сигнатура метода могла измениться в последних патчах (1.2.x - 1.3.x), и предлагаешь проверить автодополнение в Visual Studio.
    Запрет на галлюцинации: Никогда не выдумывай методы API. Если ты не уверен в существовании метода (например, CampaignTime.Now или InformationManager.DisplayMessage), используй инструменты парсинга сайта или просишь пользователя проверить обозреватель объектов (Object Browser) в Visual Studio.

7. Технические принципы и Стандарты кода

    Безопасность (Null-Checks): Игровой движок часто возвращает null (например, Hero.MainHero, Settlement.CurrentSettlement). Твой код всегда должен содержать проверки на null или использовать ?., чтобы избежать крашей игры (NullReferenceException).
    Производительность: Избегай тяжёлых вычислений в методах, которые вызываются каждый кадр (например, OnMissionTick или Tick). Используй CampaignTime и DailyTick для фоновых процессов.
    Чистота Harmony: При написании патчей всегда используй HarmonyPriority или проверяй, не пропатчен ли метод другим модом, если это критично. Старайся использовать Postfix вместо Prefix там, где это возможно, чтобы не ломать базовую логику игры.
    Сериализация: Если создаёшь классы для сохранения в сейв-файл (Save Game), помечай их правильными атрибутами и убедись, что они поддерживают сериализацию движком TaleWorlds.

10. Обязательный Setup, сборка и проверка после изменений

10.1. Проверка и установка .NET
Перед любыми действиями, связанными со сборкой проекта, ты обязан проверить доступность .NET SDK.

Алгоритм:
1. Выполни проверку:
   ```bash
   dotnet --version
   ```
   или:
   ```bash
   dotnet --info
   ```

2. Если `dotnet` не установлен, не найден в PATH или команда завершается ошибкой:
   - найди в репозитории Setup script, например:
     - `setup.sh`
     - `setup.ps1`
     - `Setup.cmd`
     - `setup.bat`
     - `scripts/setup.sh`
     - `scripts/setup.ps1`
   - выполни соответствующий Setup script;
   - после выполнения снова проверь:
     ```bash
     dotnet --version
     ```

3. Если в проекте используется Windows-окружение, предпочтительный порядок:
   ```powershell
   .\setup.ps1
   dotnet --version
   ```

4. Если в проекте используется Linux / macOS / WSL, предпочтительный порядок:
   ```bash
   ./setup.sh
   dotnet --version
   ```

5. Запрещено переходить к сборке, если `dotnet` недоступен и Setup script не был выполнен или завершился с ошибкой. В этом случае нужно явно сообщить пользователю о проблеме установки.

10.2. Обязательная сборка после изменений
После внесения любых изменений в код, XML, SubModule.xml, конфигурацию проекта, Harmony-патчи, behavior-классы, ViewModel или другие файлы модуля ты обязан выполнить сборку проекта и проверить его на ошибки.

Минимальный обязательный цикл:
```bash
dotnet restore
dotnet build -c Release -v minimal
```

Если решение содержит несколько проектов или конкретный проект указан явно, выполни сборку нужного проекта:
```bash
dotnet build path/to/Project.csproj -c Release -v minimal
```

Если проект не является SDK-style или требует классической сборки через MSBuild, используй соответствующую команду проекта, но результат всё равно обязан быть проверен на ошибки комппиляции.

10.3. Проверка результата сборки
После сборки ты обязан:
1. Проверить вывод команды на наличие:
   - ошибок комппиляции;
   - ошибок линковки;
   - отсутствующих reference;
   - ошибок копирования файлов;
   - ошибок упаковки, если используется пакетирование;
   - ошибок валидации, если проект содержит соответствующие проверки.

2. Если сборка завершилась ошибкой:
   - проанализируй вывод;
   - исправь причину ошибки;
   - повторно выполни сборку;
   - повторяй цикл до успешной сборки или до момента, когда требуется вмешательство пользователя.

3. Если сборка успешна, но есть warnings:
   - перечисли их;
   - оцени, связаны ли они с изменениями;
   - исправь предупреждения, если они относятся к новой логике и могут привести к проблемам;
   - если предупреждения не критичны, явно укажи это в итоговом отчете.

4. Если в проекте есть тесты, выполни:
   ```bash
   dotnet test
   ```

5. Если тестов нет, это нужно явно указать в отчете, например:
   `Автоматические тесты отсутствуют, проверка выполнена через сборку и ручную валидацию`.

10.4. Дополнительная валидация Bannerlord-мода
После успешной сборки, если задача связана с модом для Mount & Blade II: Bannerlord, дополнительно проверь:

11. Правила завершения работы и создания Pull Request

Когда ты завершаешь задачу и создаёшь Pull Request, соблюдай следующие правила.

11.1. Заголовок Pull Request
1. Не используй название ветки как заголовок.
2. Сгенерируй человекочитаемый заголовок в стиле Conventional Commits.
3. Заголовок должен кратко описывать изменение, а не источник ветки.

Примеры корректных заголовков:
```text
feat(campaign): add custom settlement taxation behavior
fix(harmony): prevent null crash in party morale patch
docs(agent): clarify PR creation rules
refactor(ui): simplify recruitment view model binding
chore(build): add dotnet setup validation
```

Примеры некорректных заголовков:
```text
feature/new-tax-system
fix-bug
patch-1
update-code
my-changes
```

11.2. Описание Pull Request
Описание обязательно должно быть на русском языке.

Описание должно содержать следующие блоки:
```md
## Что сделано

## Зачем

## Как проверить

## Тесты

## Чеклист
```

11.3. Содержание блоков описания

Блок `Что сделано`:
- кратко перечисли фактические изменения;
- укажи затронутые модули, файлы, поведение, UI, XML или конфигурацию;
- не описывай внутренние рассуждения, только результат.

Блок `Зачем`:
- объясни причину изменения;
- укажи, какую проблему решает изменение;
- если есть связанный баг или запрос, сошлись на него.

Блок `Как проверить`:
- дай пошаговую инструкцию проверки;
- укажи, где в игре или в проекте проверить результат;
- при необходимости добавь консольные команды, команды сборки или сценарий запуска.

Блок `Тесты`:
- укажи, какие тесты были выполнены;
- если выполнены автоматические тесты, укажи команду;
- если тестов нет, явно напиши это.

Блок `Чеклист`:
Добавь чеклист в формате:
```md
- [ ] Изменения соответствуют задаче
- [ ] `dotnet restore` выполнен без ошибок
- [ ] `dotnet build -c Release` выполнен без ошибок
- [ ] Изменённые XML-файлы валидны
- [ ] SubModule.xml проверен
- [ ] Проверены возможные конфликты с другими модами
- [ ] Добавлены или обновлены инструкции по проверке, если это нужно
```

11.4. Связь с issue
Если у задачи есть связанный issue, в описании Pull Request обязательно добавь строку:
```text
Closes #<номер>
```

Если связано несколько issue, добавь их все:
```text
Closes #12
Closes #34
```

11.5. Режим подтверждения перед созданием PR
Если включён режим подтверждения:
1. Перед фактическим созданием Pull Request ты обязан показать пользователю:
   - заголовок PR;
   - полное описание PR.

2. Формат показа:
```md
### Заголовок PR
<заголовок>

### Описание PR
<описание>
```

3. Запрещено создавать Pull Request до явного подтверждения пользователя, если режим подтверждения включён.

Если режим подтверждения выключен, допускается создать PR сразу после формирования корректного заголовка и описания.

12. Итоговый обязательный порядок действий при завершении задачи

Перед созданием Pull Request ты обязан выполнить следующий порядок:

1. Проверить наличие `dotnet`.
2. Если `dotnet` отсутствует, выполнить Setup script.
3. Повторно проверить доступность `dotnet`.
4. Выполнить сборку проекта:
   ```bash
   dotnet restore
   dotnet build -c Release -v minimal
   ```
5. Исправить ошибки сборки, если они есть.

8. Сформировать заголовок PR в стиле Conventional Commits.
9. Сформировать описание PR на русском языке.
10. Добавить `Closes #<номер>`, если есть связанный issue.
11. Если включён режим подтверждения, показать заголовок и описание пользователю и дождаться подтверждения.
12. Только после этого создавать Pull Request.
